Задание 2. Развертывание агента для решения научных задач
Цель работы
Исследовать возможности автономных ИИ-агентов, разворачиваемых на собственном сервере, как инструмента поддержки исследовательской деятельности веб-инженера: сбора и обработки источников, автоматизации рутинных этапов эксперимента, мониторинга, подготовки и публикации результатов. Оценить границы применимости такого инструмента — по надёжности, воспроизводимости, стоимости и безопасности.

Базовый материал
Основа работы — руководство по развёртыванию Hermes Agent: https://thecode.media/hermes-agent-ustanovka-nastrojka-vps/

Ключевые ориентиры из материала, которые понадобятся при планировании работы:

Hermes Agent — опенсорсный оркестратор автономных агентов с постоянной памятью, самообучением через навыки и подключением к мессенджерам, работающий на собственном сервере и не привязанный к конкретному поставщику нейросети. thecode
Архитектура агента состоит из четырёх частей: шлюзы (командная строка, Telegram, Discord, Slack, WhatsApp), инструменты (SSH, работа с файлами, браузер, планировщик), навыки (короткие инструкции с условием срабатывания и порядком шагов) и подключаемая LLM. thecode
Минимальные требования: VPS на Linux (Ubuntu 22.04+), 1 vCPU, 1 ГБ RAM при работе с облачными моделями; для локальных моделей — GPU с 8–16 ГБ видеопамяти; контекстное окно модели не менее 64 000 токенов. thecode
Память реализована файлами: MEMORY.md хранит контекст решённых задач, USER.md — предпочтения и рабочий стиль пользователя; оба файла читаются при каждом запуске. thecode
Критически важное предупреждение: агент с подключёнными инструментами выполняет команды на вашем сервере, поэтому доступ к боту равнозначен доступу к серверу. thecode
Альтернативные платформы для выполнения работы: OpenClaw (более зрелый по UX, но структурно ограниченный однамашинный ассистент) и PicoClaw — самостоятельный проект Sipeed, написанный на Go с нуля, с объёмом памяти ядра менее 10 МБ и запуском менее чем за секунду, ограничивающий доступ агента пределами его рабочего каталога и отключающий опасные команды. Требования безопасности (обязательны к выполнению до начала работы)
Работа выполняется с агентом, имеющим доступ к терминалу. До первого запуска:

Использовать отдельный VPS или виртуальную машину, не содержащую личных данных, рабочих проектов и ключей от других систем.
Создать непривилегированного пользователя; не запускать агента от root.
В списке разрешённых пользователей шлюза указать только свой идентификатор; режим «разрешить всем» не включать ни при каких условиях.
Все ключи и токены хранить вне репозитория; при случайной публикации — немедленно отозвать и перевыпустить.
Установить жёсткий лимит расходов на стороне LLM-провайдера до первого запуска агента с планировщиком.
Все эксперименты с небезопасными сценариями (задание P5) выполнять только на изолированной машине и только над собственными ресурсами.
Ход работы
Арендовать VPS (Linux, Ubuntu 22.04+, минимум 1 vCPU / 1 ГБ RAM) или развернуть локальную виртуальную машину. Зафиксировать параметры: провайдер, тариф, регион размещения, стоимость.
Выполнить базовую настройку сервера: непривилегированный пользователь, доступ по SSH-ключу, отключение входа по паролю, firewall, обновление пакетов. Зафиксировать выполненные шаги.
Установить Docker и Docker Compose. Проверить работоспособность: docker run --rm hello-world.
Выбрать LLM-провайдера и получить API-ключ (OpenRouter как агрегатор, прямой ключ провайдера, портал разработчика агента либо Ollama для локальной модели). Проверить соответствие модели требованию по размеру контекстного окна.
Установить лимит расходов и/или ограничение по количеству запросов в личном кабинете провайдера. Зафиксировать установленные значения.
Подготовить шлюз: создать Telegram-бота через @BotFather, получить токен, узнать собственный числовой идентификатор пользователя.
Запустить мастер настройки агента в контейнере, смонтировав каталог конфигурации с хоста. Убедиться, что конфигурация записана именно в тот каталог, который будет подключён при запуске.
Описать compose.yaml: образ, имя контейнера, политика перезапуска unless-stopped, команда запуска шлюза, монтирование каталога данных. Проверить соответствие точки монтирования ожидаемому агентом пути.
Запустить контейнер в фоновом режиме и просмотреть логи. Контрольный признак корректного старта — ненулевое число загруженных навыков и отсутствие предупреждения об отключённых платформах обмена сообщениями.
Проверить связку в деле: отправить боту сообщение и получить ответ. Зафиксировать время отклика.
Ограничить доступ: в списке разрешённых пользователей оставить только собственный идентификатор, проверить, что бот не отвечает постороннему аккаунту (проверку выполнить с тестового аккаунта).
Настроить память: заполнить USER.md (предметная область, рабочий стиль, формат ответов, язык) и MEMORY.md (контекст исследовательской задачи, договорённости). Проверить, что агент опирается на эти файлы, задав вопрос, ответ на который возможен только с их учётом.
Подключить и проверить инструменты, необходимые для исследовательских задач: веб-поиск, загрузка и чтение страниц, работа с файлами, запуск команд, планировщик.
Создать первый навык (skill) и убедиться, что он срабатывает по описанным условиям.
Поставить задачу по расписанию (cron) и дождаться её автономного выполнения. Зафиксировать результат и журнал.
Настроить сохранение логов агента (ротация, объём, срок хранения) — они понадобятся для заданий T4 и P4.
Отладить работу, зафиксировав возникшие ошибки, гипотезы и решения.
