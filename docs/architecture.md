# Архитектура управления подготовительным стендом

Все девять команд `scripts/lab.sh` вызывают пакет `src/agent_lab`.
Оболочка определяет корень проекта и передаёт аргументы через `exec`.
Сценарий запуска проверяет уже работающие компоненты и
при ошибке освобождает только ресурсы текущей попытки. Публичные команды
оболочки сохранены.

Стиль следует референсу `user_service`: прикладные операции группируются
в областях `application/stand`, `model`, `deployment` и `hermes`,
с каталогами `commands`, `queries` и `interfaces`. Обработчики
`*Handler` вызываются через `__call__`, инфраструктурные реализации имеют
суффикс `Impl`. Конфигурация оформлена dataclass-моделью `RuntimeConfig`,
сборка находится в `main/di.py`. Тесты используют pytest, отдельные каталоги
unit/integration, fixtures и mocks.

Оформление Python-кода, shell-помощников и Makefile следует
`fastapi-clean-example`. Порты используют `Protocol` и `@abstractmethod`,
DTO — dataclass с `slots`. Правила инструментов объединены в `pyproject.toml`;
подробности приведены в [соглашениях по разработке](code-style.md).

Application зависит от протоколов, инфраструктура выполняет внешние эффекты,
а `main` соединяет реализации. Направление импортов проверяется тремя
контрактами `import-linter`, типы — строгим `mypy`. Domain не выделен:
собственных исследовательских правил у CLI нет. Синхронному CLI
достаточно стандартной библиотеки. Собственный Telegram-бот выделен
в независимый пакет `src/agent_bot`: он использует asyncio, aiogram,
HTTPX и Dishka. Его структура по референсу `crudik` описана в
[документации бота](telegram-bot.md); четыре дополнительных контракта
импортов защищают границы его слоёв.

## Запуск и владение ресурсами

`LAB_OLLAMA_BACKEND=mac|docker` читается и проверяется в `main/run.py`.
Значение по умолчанию — `mac`. Сборка передаёт сценарию запуска нужный
порядок компонентов: VM → Ollama → туннель для Mac; VM → Ollama для Docker.
Application сохраняет владение запуском и откатом; инфраструктура выбирает
launchd либо Compose. `DockerOllamaImpl` проверяет принадлежность контейнера
проекту, память VM и готовность API. Перед первым запуском модели он
переносит файлы развёртывания и подготавливает отдельный каталог моделей.
Существующий контейнер проверяется без пересоздания. При ошибке запуска
останавливается также контейнер с завершившимся процессом, чтобы отключить
его автоматические попытки перезапуска. Текущий backend нужно остановить
до переключения; общее `stop` удаляет контейнеры всех профилей, сохраняя данные.
Конфигурация Hermes не зависит от выбора: Ollama доступна на loopback VM.
Параметры и реальные замеры приведены в [инструкции Ollama](ollama-backends.md).

Под общей блокировкой обработчик проходит компоненты в порядке VM → Ollama
→ туннель. Работающую VM и загруженные launchd-сервисы он проверяет,
сохраняя их процессы. Остановленная VM запускается по имени; новая — по
шаблону Lima. Отсутствующие launchd-сервисы запускаются через bootstrap.
Загруженный, но неисправный сервис остаётся для диагностики: `start`
не выполняет bootout или kickstart для такого сервиса.

Компонент регистрируется для очистки до запуска внешней команды. Поэтому
ошибка или тайм-аут после создания VM либо загрузки launchd-job не теряет
учёт ресурса. При сбое, отмене или неожиданном исключении обработчик
освобождает зарегистрированные компоненты в обратном порядке. Ресурсы,
которые работали до этой попытки, в этот список не попадают. Ошибка очистки
одного компонента не прерывает остальные операции, её сообщение добавляется
к исходной ошибке; исходный код завершения сохраняется.

Очистка выгружает новые launchd-job и останавливает запущенную этой попыткой
VM. Диски, модели, данные агента, plist, каталоги и логи сохраняются. Это
освобождение работающих ресурсов, а не удаление пользовательских данных
или отмена произвольных изменений внутри VM.

Проверка готовности требует SSH-доступа в VM, PID Ollama и корректного
ответа `/api/version` на Mac, PID туннеля и ответа API из VM. Одного
успешного bootstrap или HTTP-кода недостаточно. PID проверяется до и после
API-запроса. Загрузка модели, генерация ответа Hermes и Telegram проверяются
отдельно.

SSH-туннель использует параметры `ControlMaster=no`, `ControlPath=none`,
`ControlPersist=no` поверх SSH-config Lima. Это оставляет перенаправление
в отдельном процессе launchd и позволяет освободить порт при его остановке.
Конфигурация общего SSH-соединения Lima для других команд не изменяется.

`start` и `stop` удерживают `lifecycle.lock` вне репозитория до завершения
всего сценария. Отдельные процессы CLI не могут одновременно изменить
снимок запуска и список владельцев. Файл блокировки не удаляется, чтобы
все вызовы продолжали блокировать один inode. Ручные команды `limactl`
и `launchctl` не участвуют в этой блокировке.

Явный `stop` сохраняет порядок: туннель, Ollama, Compose down, VM. Если VM
уже остановлена, Compose down пропускается. `scripts/local-services.py`
удалён после переноса всех его вызывающих команд: управление launchd имеет
одну реализацию в типизированном адаптере.

## Контракты и ограничения времени

`status` по-прежнему последовательно выполняет Lima list, Ollama ps и
Compose ps, передавая вывод в терминал. `model` сначала выполняет pull,
затем create. `web-deps` устанавливает DDGS перед agent-browser. `gateway`
проверяет конфигурацию и доступность API перед Compose up. Сбой прекращает
следующие шаги и сохраняет код завершения внешней команды.

Аргументы `chat` передаются в Hermes буквально, включая пробелы, кавычки,
`--` и `--help`. Вызов без команды, `help` и неизвестная команда сохраняют
прежнюю строку Usage и код 0. `start`, `stop`, `status` отклоняют лишние
аргументы, остальные команды подготовки продолжают их игнорировать.
Python-пакет и dev-зависимости устанавливать для
управления не требуется; нужен Python 3.13+.

`sync` формирует временный архив `infra/hermes`, `infra/bot`, `infra/ollama`, `templates`,
`src/agent_bot`, `pyproject.toml`, `uv.lock` и `.dockerignore`, исключая
`__pycache__` и `*.pyc`. Python tarfile не переносит расширенные
атрибуты macOS. Архив передаётся в stdin гостевого tar; файловый дескриптор
остаётся у создавшего его адаптера и закрывается также при ошибке.
После передачи запускается `sudo python3 .../infra/hermes/provision.py`.
Конфигурация, `.env`, USER.md и MEMORY.md создаются только при отсутствии.
Skill и правила хранения журналов обновляются. Каждый устанавливаемый файл
подготавливается рядом с назначением и заменяется через rename: ссылка в
назначении заменяется файлом, её цель не переписывается. Общей транзакции
для файлов и systemd нет; повторный вызов продолжает подготовку, сохраняя
существующие настройки и память. Установщик проверен на Python 3.12 в VM.

| Операция | Ограничение |
| --- | --- |
| Lima start | 600 секунд |
| Ожидание блокировки | 60 секунд |
| Проверка готовности каждого локального сервиса | 30 секунд |
| Отдельный launchctl | 10 секунд; bootstrap допускает четыре попытки при временно занятом label |
| Отдельная проверка PID/API в цикле готовности | 3 секунды, с учётом остатка общего срока |
| SSH-проверка VM, запрос `status` или проверка статуса VM | 30 секунд |
| Compose down или Lima stop | 60 секунд |
| Ollama pull / create | 1800 / 300 секунд |
| Передача архива / гостевой установщик | По 120 секунд |
| Отдельный systemctl внутри установщика | 30 секунд |
| Установка каждой web-зависимости | 900 секунд |
| Preflight шлюза | 120 секунд |
| Сборка и запуск Compose | 900 секунд; ожидание здоровья сервисов — 90 секунд |
| Установка зависимостей API в мастере бота / отдельное изменение конфигурации Hermes | 900 / 60 секунд |
| Проверка API перед шлюзом | curl 5 секунд, весь вызов Lima 30 секунд |
| Мастер настройки / диалог | До 24 часов на вызов |

При тайм-ауте или Ctrl+C ProcessRunner завершает группу foreground-команды
и забирает код дочернего процесса до возврата управления обработчику.
Демоны launchd и VM освобождает сценарий запуска. Код тайм-аута — 124,
Ctrl+C — 130; сигнал дочернего процесса преобразуется в `128 + номер сигнала`.
Обычные внешние ошибки показываются без Python traceback. Неожиданные
ошибки программирования после очистки продолжают распространяться.

Для команд с пользовательским вводом процесс остаётся в той же сессии
терминала, в отдельной группе. CLI передаёт ей foreground-терминал и
возвращает его после завершения или тайм-аута. Ctrl+C доставляется
интерактивной команде. При перенаправлении stdin потоки передаются напрямую.
ProcessRunner освобождает локальную группу; состояния внешних демонов и
возможные частичные изменения Docker не являются файловой транзакцией.

## Проверки разработки

```sh
uv sync --locked
make check
```

Зависимости бота и dev-инструментов закреплены в `uv.lock`; CLI использует
стандартную библиотеку. `make check` и `make check-ci` проверяют Ruff, форматирование Python
и TOML, deptry, ShellCheck, slotscheck, Self-checker, типы, импорты и все тесты.
Профиль Ruff использует `ALL`, длину строки 120
и объединение импортов как в референсе. Исключения описаны в конфигурации;
`Any`, `noqa` и `type: ignore` в новом коде не используются. Гостевой
`provision.py`, контейнерный `preflight.py`, мастер бота и поддерживаемые Python-скрипты
включены в Ruff и строгий mypy. Синтаксис Bash и ShellCheck проверяют все
shell-скрипты проекта. `make format` отдельно применяет безопасные исправления
и форматирование; команды проверки исходники не меняют.

Проверки оболочки используют временный HOME и заглушки Lima, Ollama,
launchctl и curl, не затрагивая настоящий стенд. Они проверяют повторный
и параллельный запуск, частичный сбой, сохранение существующих компонентов
и данных, ошибки очистки и прежние команды диагностики. ProcessRunner и
файловая блокировка проверяются настоящими короткими дочерними процессами.
OpenSSH `-G` проверяет эффективные параметры туннеля поверх конфигурации Lima.
Оставшиеся команды проверяются по порядку эффектов, argv и прекращению шагов
при ошибке. Отдельные проверки файлов используют временные каталоги и
настоящие права файлов; псевдотерминал проверяет ввод, Ctrl+C и возврат
foreground-группы после тайм-аута.

При переносе остальных сценариев `make check` прошёл: 88 тестов без пропусков, Ruff и mypy проверили
85 файлов, все три контракта импортов соблюдены. Отдельная проверка архитектуры
подтвердила, что обработчики управляют порядком и владением, а адаптеры —
внешними процессами и блокировкой. Проверка выполнена в этой рабочей сессии;
она не заменяет независимое ревью.

После оформления по `fastapi-clean-example` локальный `make check-ci` прошёл:
106 тестов без пропусков, 94 Python-файла проверены Ruff и mypy, все три
контракта импортов соблюдены. Набор включает Bash-синтаксис, ShellCheck,
TOML, deptry, slotscheck и проверку Self. Дополнительное сравнение старого
и нового `preflight.py` на 18 наборах искусственных настроек подтвердило
одинаковые коды завершения, сообщения и порядок чтения конфигурации.
Это локальная проверка подготовки; workflow на GitHub выполняется после публикации.

На предыдущем этапе 10 октября 2026 года выполнена проверка на настоящей
существующей VM. Контролируемый сбой после готовности туннеля остановил все
компоненты текущей попытки. При повторном `start` PID VM, Ollama и туннеля
сохранились. Другой сбой удалил только новый туннель, сохранив PID ранее
работавших VM и Ollama; API в VM после очистки стал недоступен. Финальные
`start` и `status` успешны, API на Mac и в VM сообщает `0.35.1`. Стенд
оставлен работающим. Результаты сохранены в
[проверке жизненного цикла](../evidence/preparation/startup-lifecycle.json).

Создание новой настоящей VM и генерация ответа моделью в этой проверке
не выполнялись. Подтверждения предыдущих этапов сохранены отдельно:
[выделение сценариев](../evidence/preparation/refactor-step-01.json) и
[адаптация стиля](../evidence/preparation/style-user-service.json).

После переноса остальных сценариев на настоящей VM выполнен повторный
`sync`: содержимое, mtime, права и владельцы четырёх защищённых файлов
сохранены, таймер хранения журналов активен. `chat --help` прошёл в настоящем
терминале с кодом 0. Мастер Telegram, загрузка модели, установка зависимостей
и запуск шлюза в этой проверке не выполнялись; их вызовы проверены заглушками.
Результаты и ограничения записаны в
[проверке переноса остальных сценариев](../evidence/preparation/python-scenarios.json).
