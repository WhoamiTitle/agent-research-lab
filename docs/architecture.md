# Архитектура управления подготовительным стендом

Команды `start`, `stop` и `status` из `scripts/lab.sh` вызывают пакет
`src/agent_lab`. Сценарий запуска проверяет уже работающие компоненты и
при ошибке освобождает только ресурсы текущей попытки. Публичные команды
оболочки сохранены.

Стиль следует референсу `user_service`: прикладные операции группируются
в `application/stand/commands`, `queries` и `interfaces`. Обработчики
`*Handler` вызываются через `__call__`, инфраструктурные реализации имеют
суффикс `Impl`. Конфигурация оформлена dataclass-моделью `RuntimeConfig`,
сборка находится в `main/di.py`. Тесты используют pytest, отдельные каталоги
unit/integration, fixtures и mocks.

## Ответственность

| Часть | Ответственность |
| --- | --- |
| `presentation/cli/main.py` | Выбор операции, сообщение о готовности, вывод ошибок и код завершения |
| `application/stand/commands/start_stand.py` | Порядок запуска, учёт ресурсов попытки и обратная очистка |
| `application/stand/commands/stop_stand.py` | Явная остановка под той же блокировкой |
| `application/stand/components.py` | Три компонента стенда и порядок их запуска |
| `application/stand/queries/get_stand_status.py` | Последовательность команд диагностики |
| `application/stand/interfaces/runtime.py` | Контракты жизненного цикла и диагностики |
| `application/common/exceptions.py` | Прикладная ошибка внешней операции с кодом завершения |
| `infrastructure/runtime/main.py` | Lima, Compose и проверка готовности процессов/API |
| `infrastructure/runtime/launchd.py` | Проверка launchd, создание plist, bootstrap и bootout |
| `infrastructure/runtime/lock.py` | Межпроцессная файловая блокировка с ограниченным ожиданием |
| `infrastructure/runtime/config.py` | Типизированные пути и тайм-ауты |
| `infrastructure/process.py` | Запуск команды, захват вывода, завершение процессов при отмене |
| `main/run.py`, `main/di.py` | Загрузка путей и сборка зависимостей |

Application зависит от протоколов, инфраструктура выполняет внешние эффекты,
а `main` соединяет реализации. Направление импортов проверяется тремя
контрактами `import-linter`, типы — строгим `mypy`. Domain не выделен:
собственных исследовательских правил на этом этапе нет. Синхронному CLI
достаточно стандартной библиотеки; веб-фреймворк и asyncio не добавлены.

## Запуск и владение ресурсами

Под общей блокировкой обработчик проходит компоненты в порядке VM → Ollama
→ туннель. Работающую VM и загруженные launchd-сервисы он проверяет,
сохраняя их процессы. Остановленная VM запускается по имени; новая — по
шаблону Lima. Отсутствующие launchd-сервисы запускаются через bootstrap.
Загруженный, но неисправный сервис остаётся для диагностики: `start`
не выполняет bootout или kickstart для такого сервиса.

Компонент регистрируется для очистки до запуска внешней команды. Поэтому
ошибка или тайм-аут после создания VM либо загрузки launchd-job не теряет
учёт ресурса. При сбое, отмене или неожиданном исключении обработчик
освобождает зарегистрированные компоненты в обратном порядке. Ресурсы,
которые работали до этой попытки, в этот список не попадают. Ошибка очистки
одного компонента не прерывает остальные операции, её сообщение добавляется
к исходной ошибке; исходный код завершения сохраняется.

Очистка выгружает новые launchd-job и останавливает запущенную этой попыткой
VM. Диски, модели, данные агента, plist, каталоги и логи сохраняются. Это
освобождение работающих ресурсов, а не удаление пользовательских данных
или отмена произвольных изменений внутри VM.

Проверка готовности требует SSH-доступа в VM, PID Ollama и корректного
ответа `/api/version` на Mac, PID туннеля и ответа API из VM. Одного
успешного bootstrap или HTTP-кода недостаточно. PID проверяется до и после
API-запроса. Загрузка модели, генерация ответа Hermes и Telegram проверяются
отдельно.

SSH-туннель использует параметры `ControlMaster=no`, `ControlPath=none`,
`ControlPersist=no` поверх SSH-config Lima. Это оставляет перенаправление
в отдельном процессе launchd и позволяет освободить порт при его остановке.
Конфигурация общего SSH-соединения Lima для других команд не изменяется.

`start` и `stop` удерживают `lifecycle.lock` вне репозитория до завершения
всего сценария. Отдельные процессы CLI не могут одновременно изменить
снимок запуска и список владельцев. Файл блокировки не удаляется, чтобы
все вызовы продолжали блокировать один inode. Ручные команды `limactl`
и `launchctl` не участвуют в этой блокировке.

Явный `stop` сохраняет порядок: туннель, Ollama, Compose down, VM. Если VM
уже остановлена, Compose down пропускается. `scripts/local-services.py`
удалён после переноса всех его вызывающих команд: управление launchd имеет
одну реализацию в типизированном адаптере.

## Контракты и ограничения времени

`status` по-прежнему последовательно выполняет Lima list, Ollama ps и
Compose ps, передавая вывод в терминал. Аргументы `chat` и остальные ветки
оболочки сохранены. Python-пакет и dev-зависимости устанавливать для
управления не требуется; нужен Python 3.13+.

| Операция | Ограничение |
| --- | --- |
| Lima start | 600 секунд |
| Ожидание блокировки | 60 секунд |
| Проверка готовности каждого локального сервиса | 30 секунд |
| Отдельный launchctl | 10 секунд; bootstrap допускает четыре попытки при временно занятом label |
| Отдельная проверка PID/API в цикле готовности | 3 секунды, с учётом остатка общего срока |
| SSH-проверка VM, запрос `status` или проверка статуса VM | 30 секунд |
| Compose down или Lima stop | 60 секунд |

При тайм-ауте или Ctrl+C ProcessRunner завершает группу foreground-команды
и забирает код дочернего процесса до возврата управления обработчику.
Демоны launchd и VM освобождает сценарий запуска. Код тайм-аута — 124,
Ctrl+C — 130; сигнал дочернего процесса преобразуется в `128 + номер сигнала`.
Обычные внешние ошибки показываются без Python traceback. Неожиданные
ошибки программирования после очистки продолжают распространяться.

## Проверки разработки

```sh
uv sync --locked
make check
```

Dev-зависимости закреплены в `uv.lock`; runtime использует стандартную
библиотеку. `make check` проверяет Ruff, форматирование, типы, импорты,
pytest и синтаксис `lab.sh`. Профиль Ruff использует `ALL`, длину строки 120
и объединение импортов как в референсе. Исключения описаны в конфигурации;
`Any`, `noqa` и `type: ignore` в новом коде не используются. Унаследованный
контейнерный `preflight.py` остаётся вне строгой проверки mypy.

Проверки оболочки используют временный HOME и заглушки Lima, Ollama,
launchctl и curl, не затрагивая настоящий стенд. Они проверяют повторный
и параллельный запуск, частичный сбой, сохранение существующих компонентов
и данных, ошибки очистки и прежние команды диагностики. ProcessRunner и
файловая блокировка проверяются настоящими короткими дочерними процессами.
OpenSSH `-G` проверяет эффективные параметры туннеля поверх конфигурации Lima.

Финальный `make check` прошёл: 53 теста без пропусков, Ruff и mypy проверили
51 файл, все три контракта импортов соблюдены. Отдельная проверка архитектуры
подтвердила, что обработчики управляют порядком и владением, а адаптеры —
внешними процессами и блокировкой. Проверка выполнена в этой рабочей сессии;
она не заменяет независимое ревью.

10 октября 2026 года также выполнена отдельная проверка на настоящей
существующей VM. Контролируемый сбой после готовности туннеля остановил все
компоненты текущей попытки. При повторном `start` PID VM, Ollama и туннеля
сохранились. Другой сбой удалил только новый туннель, сохранив PID ранее
работавших VM и Ollama; API в VM после очистки стал недоступен. Финальные
`start` и `status` успешны, API на Mac и в VM сообщает `0.35.1`. Стенд
оставлен работающим. Результаты сохранены в
[проверке жизненного цикла](../evidence/preparation/startup-lifecycle.json).

Создание новой настоящей VM и генерация ответа моделью в этой проверке
не выполнялись. Подтверждения предыдущих этапов сохранены отдельно:
[выделение сценариев](../evidence/preparation/refactor-step-01.json) и
[адаптация стиля](../evidence/preparation/style-user-service.json).
