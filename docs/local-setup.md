# Локальное управление стендом

Все команды выполняются из корня `agent-research-lab` на macOS ARM64.
Среда создаётся отдельно от остальных проектов. Git инициализирован;
первый коммит с README отправлен в `origin/main`.

## Состав

- Ollama: на macOS с GPU Apple (по умолчанию) либо в Docker на CPU VM.
- Lima VM `agent-research`: Ubuntu 24.04 ARM64, 2 CPU, 10 GiB RAM, диск 24 GiB.
- В VM: Docker Engine, Compose и Hermes с закреплённым образом.
- Состояние Hermes: `/srv/agent-lab/data` внутри VM, монтируется в `/opt/data`.
- Собственный Telegram-бот: отдельный контейнер, код в `src/agent_bot`.
- Секреты бота: `/srv/agent-lab/bot/.env` внутри VM, права `0600`, UID 10000.
- Модели, служебные plist и логи Mac: `~/.local/share/agent-research-lab/`.
- VM и её служебный SSH-ключ: `~/.lima/`, вне проекта.

В режиме `mac` Ollama слушает только `127.0.0.1:11434` на Mac. Обратный SSH-туннель делает
тот же адрес доступным в VM. Контейнер использует сеть **этой VM** через
`network_mode: host`; каталоги Mac и Docker-сокет ему не предоставляются.
Firewall блокирует исходящий доступ к частным сетям, сохраняя DNS Lima.
Это отдельный учебный стенд, а не гарантия защиты от всех уязвимостей.
В режиме `docker` тот же порт обслуживает контейнер Ollama внутри VM;
модель и SSH-туннель на Mac не запускаются. Выбор режима, переключение
и сравнение скорости описаны в [инструкции Ollama](ollama-backends.md).

## Запуск и остановка

```sh
./scripts/lab.sh start
./scripts/lab.sh status
```

В режиме `mac` `start` запускает отсутствующие компоненты: VM, Ollama и туннель. Повторная
команда проверяет готовность, сохраняя PID работающих сервисов. Проверяются
SSH в VM, процесс Ollama и `/api/version` на Mac, процесс туннеля и тот же
API из VM. Загрузка модели и генерация ответа в эту проверку не входят.
Шлюз Telegram включается отдельно.

При ошибке или Ctrl+C команда освобождает компоненты, которые начала
запускать сама, в обратном порядке. Ранее работавшие компоненты сохраняются.
Диски VM, модели, данные агента, настройки и журналы не удаляются.
Если очистка не удалась, ошибка перечисляет оставшиеся проблемы.
Загруженный, но неисправный сервис автоматически не перезапускается:
команда сообщает ошибку для диагностики. Логи находятся в
`~/.local/share/agent-research-lab/logs/`.

`start` и `stop` используют общую файловую блокировку. Ожидание другого
запуска ограничено 60 секундами; при превышении возвращается код 124.
Все команды `scripts/lab.sh` делегируются Python-пакету `src/agent_lab`;
нужен Python 3.13+, установка dev-зависимостей для управления не требуется.
Внутренняя структура и проверки описаны в [архитектуре](architecture.md).
Два launchd-сервиса работают в текущей пользовательской сессии macOS;
plist не установлен в `~/Library/LaunchAgents`. После выхода из аккаунта
нужно снова выполнить `start`. Сон или выключение Mac прерывает стенд.
Туннель использует отдельное SSH-соединение: ControlMaster Lima отключён
для этого процесса, чтобы остановка сервиса освобождала его перенаправление.

17 октября 2026 года проверен ребут гостевой Linux VM при работающем Mac:
Docker сам восстановил Hermes и бота, launchd переподключил туннель,
а контрольный ответ через Ollama успешно отправился в Telegram.
Первая попытка запуска бота завершилась ошибкой; автоматический повтор
Docker восстановил polling через 18,96 секунды от команды перезагрузки.
Ручные команды запуска после ребута не выполнялись. Протокол и границы —
в [проверке P1](p1.md#восстановление-после-перезагрузки-vm) и
[снимках окружения](../evidence/p1/vm-reboot.json).

```sh
./scripts/lab.sh stop
```

Остановка сохраняет диски VM, настройки и модели. Docker Desktop не
используется этими командами; его выбранный context не переключается.

## Воспроизведение подготовки

```sh
brew install lima ollama
./scripts/lab.sh start
./scripts/lab.sh model
./scripts/lab.sh sync
./scripts/lab.sh web-deps
```

`model` загружает `qwen3.5:4b` и создаёт локальный `agent-lab-qwen:4b`
с `num_ctx=65536` и ограничением ответа 2048 токенов. Исходный тег модели
может меняться; фактический digest нужно фиксировать при новом скачивании.

`sync` переносит `infra/hermes/`, `infra/bot/`, `infra/ollama/`, `templates/`, `src/agent_bot/`,
`pyproject.toml`, `uv.lock` и `.dockerignore` в VM. Конфигурация,
`.env` и память создаются только при их отсутствии, чтобы не перезаписать
уже введённые настройки. Для изменения существующих файлов нужно отдельно
редактировать их в VM. Диагностический skill обновляется из шаблона.
Файлы устанавливает `infra/hermes/provision.py` внутри VM; архив и временные
файлы установки освобождаются после операции. Повторный `sync` проверен
с сохранением содержимого, времени изменения, прав и владельцев настроек
и памяти. Результаты — в [проверке переноса сценариев](../evidence/preparation/python-scenarios.json).

Для внешних операций заданы тайм-ауты в `RuntimeConfig`. Интерактивные
`setup` и `chat` сохраняют ввод и терминал, длительность каждого вызова
ограничена 24 часами. Полная таблица ограничений находится в
[описании архитектуры](architecture.md).

## Настройка Hermes и Telegram

Модель текущего стенда уже настроена. После создания отдельного бота через
`@BotFather` (`/newbot`) выполнить в локальном терминале:

```sh
./scripts/lab.sh start
./scripts/lab.sh setup --gateway-only
```

`setup --gateway-only` запускает `infra/bot/setup.py` внутри VM и сохраняет
параметры Ollama. Обычный `setup` открывает полный мастер Hermes.

1. Ввести токен от `@BotFather` в скрытое поле локального терминала.
2. Ввести один собственный числовой Telegram ID во второе скрытое поле.
   Пустой ввод сохраняет ранее введённое значение.
3. Дождаться установки зависимостей API в управляемое окружение Hermes и
   сохранения настроек. Используется официальный extra `messaging`:
   доступность `aiohttp` в базовом окружении образа недостаточна.

Токен и ID сохраняются в `/srv/agent-lab/bot/.env` внутри VM.
Мастер создаёт случайный ключ локального API, записывает его в окружения
обоих сервисов и отключает встроенный Telegram-адаптер Hermes. Повторная
настройка сохраняет этот ключ. До изменения создаётся приватная копия
файлов в `/srv/agent-lab/backups/bot-setup-*`; при ошибке настройки
содержимое и права файлов восстанавливаются. Установленные зависимости
не откатываются вместе с файлами.
Реальные значения не вставлять в чат, команды shell и репозиторий.

В `TELEGRAM_ALLOWED_USERS` должен быть ровно собственный ID.
`TELEGRAM_ALLOW_ALL_USERS`, `GATEWAY_ALLOW_ALL_USERS` и `TELEGRAM_GUEST_MODE`
остаются `false`; общий `GATEWAY_ALLOWED_USERS` и групповые списки пусты.
Актуальное имя флага Hermes — `TELEGRAM_ALLOW_ALL_USERS`; прежний
`TELEGRAM_ALLOW_ALL` не управляет разрешением доступа.

Собственный обработчик принимает сообщения только от владельца в личном
чате; группы и посторонние сообщения игнорируются до вызова модели.
`platforms.telegram.enabled` в Hermes должен быть `false`, а
`platforms.api_server.enabled` — `true`. API слушает `127.0.0.1:8642`
внутри VM и требует Bearer-ключ для запуска агента.

Фактический отказ постороннему проверяется отдельно по [протоколу P1](p1.md).

```sh
./scripts/lab.sh gateway
```

Команда сначала проверяет локальный provider, контекст, отсутствие fallback,
токен и ограничения доступа. При незавершённой настройке запуск отклоняется.
Затем команда собирает образ бота и запускает оба контейнера с
`restart: unless-stopped`; бот ожидает успешной проверки здоровья Hermes.
Проверка содержимого конфигурации не заменяет проверку ответов бота
с двух аккаунтов.

В собственном боте `/start` и `/help` возвращают справку без вызова модели,
а `/status` проверяет доступность API Hermes. Для проверки генерации отправить
обычный текст, например «Ответь одним словом: готов».
Структура кода, тайм-ауты и границы доставки описаны в
[документации бота](telegram-bot.md).

Для установки с нуля полный `./scripts/lab.sh setup` позволяет задать модель.
Выбрать пользовательский OpenAI-compatible endpoint:

- URL: `http://127.0.0.1:11434/v1`.
- Модель: `agent-lab-qwen:4b`.
- Ключ-заглушка локального endpoint: `ollama-local`.
- Контекст: 65536. Облачные резервные модели не добавлять.

## CLI и технический навык

Telegram для локального диалога не нужен. CLI использует тот же Ollama,
память, навыки и рабочий каталог внутри VM.

```sh
./scripts/lab.sh chat --cli
```

Это интерактивный диалог в терминале; выход — `/exit`.
Аргументы Hermes можно передавать после `chat`. Для одного ответа без
интерактивного режима:

```sh
./scripts/lab.sh chat --oneshot -Q -q 'Какова диагностическая метка лаборатории?'
```

Навык можно явно подгрузить в начале диалога:

```sh
./scripts/lab.sh chat --cli -s lab-readiness
```

В проверке подготовки 10 октября общий запрос готовности не привёл к чтению навыка,
а модель дала неверные выводы о Docker и GPU. Этот ответ сохранён в журнале
ошибок. Docker находится в VM, а Ollama использует GPU Mac; отсутствие
Docker-сокета внутри Hermes предусмотрено изоляцией.

Для проверки исходной памяти спросить диагностическую метку стенда, не
подсказывая её в запросе. Для технического навыка запросить:
«Проверь готовность лабораторного стенда». Сверять ответ с реальным выводом
инструментов. Создание шаблона само по себе не подтверждает использование памяти
или навыка агентом.

17 октября явный запрос через Hermes API подтвердил последовательность
`skills_list` → `skill_view(name=lab-readiness)` → `terminal`. Каталог
вернул 54 доступных навыка; прочитанное содержимое совпало с шаблоном.
Команды подтвердили UID 10000, рабочий каталог и `WORKSPACE_OK`.
Трасса и границы проверки находятся в
[материалах P1](../evidence/p1/skill-loading.json).
В закреплённом образе HTTP-каталог `GET /v1/skills` содержит ошибку
`include_editorial` и возвращает 500; штатные инструменты навыков работают.

В конфигурации включены терминал, файлы, память, навыки, бесплатный поиск DDGS
и локальный браузер. Дополнительная зависимость DDGS устанавливается через
менеджер Hermes командой `web-deps`, не в Python на Mac.
`web-deps` также устанавливает CLI `agent-browser`, необходимый для
регистрации browser_navigate; одного Chromium в образе недостаточно.
Для Hermes v0.21.6 задано `browser.backend: "off"`: это отключает
автоматический выбор Browser Use CLI и включает встроенные `browser_*`.
`browser.cloud_provider: local` закрепляет локальный Chromium.
CLI также получает инструменты планировщика. В подготовке 10 октября
одноразовую задачу с `deliver: local` обслуживал временный цикл
`hermes cron tick`. Отдельная проверка P1 17 октября подтвердила выполнение
самим постоянным шлюзом при закрытом клиенте Telegram, по подтверждению
пользователя. Вызов `terminal` создал файл от UID 10000; история содержит
`source=builtin` и `status=completed`. Начальная попытка с `python -c`
была заблокирована; для повтора использованы обычные shell-команды,
настройки подтверждений не менялись. Оба контрольных расписания удалены,
действующих задач нет. Материалы — в
[протоколе cron P1](../evidence/p1/autonomous-cron.json).
Платные API для поиска или чтения страниц не подключены.

## Журналы и расходы

Для отображения событий используется `America/Los_Angeles` с учётом
сезонного перевода часов. При разборе исходных журналов время переводится
из зоны источника; в отчёте указываются дата и смещение UTC.

Docker stdout/stderr: `json-file`, максимум 10 MB на файл, 3 файла на контейнер.
Для обычных `.log` в каталоге Hermes установлен logrotate: ежедневно,
`maxsize 10M`, 7 архивов, `maxage 14`. Это проверяется периодическим запуском
logrotate; не является мгновенным жёстким лимитом объёма всех данных.
SQLite, разговоры и логи s6 `current` не переписываются этим правилом.
Для шлюза в выбранном образе s6 хранит до 10 архивов с порогом ротации
1 000 000 байт. Отдельный ежедневный systemd-таймер удаляет только законченные
архивы `@*.s`, чей `mtime` старше 14 суток. Текущий открытый лог сохраняется.
Этот таймер обслуживает журналы и не запускает задачи ИИ-агента.

Оплата API отсутствует: используется локальный Ollama без платного fallback.
Для отдельного сервиса Ollama задано `OLLAMA_NO_CLOUD=1`, запрещающее
облачные возможности Ollama. Загрузка весов модели и web-поиск требуют интернета.
Это не означает нулевую стоимость электричества и оборудования. Вместо
кабинета провайдера ограничены параллельность модели (1), число загруженных
моделей (1) и итерации Hermes (8). Эти настройки не являются денежным лимитом.

Полные логи и состояние остаются приватными в VM и локальном runtime.
В репозитории сохраняются только проверенные результаты технической подготовки.
