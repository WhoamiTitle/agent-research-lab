# P1 Развёртывание и автономность агента

**Статус: выполняется.** P1 начато 15 октября 2026 года на отдельной локальной
VM с Hermes и Ollama. Инфраструктура проверена; 16 октября Telegram-шлюз
подключился в режиме polling. Затем добавлен собственный Telegram-код перед
Hermes: aiogram → локальный Hermes API → Ollama. Контрольный Telegram-диалог
подтверждён 16 октября. 17 октября подтверждены каталог навыков и полная
загрузка диагностического `lab-readiness` с выполнением его команд.
В тот же день проверено автоматическое восстановление Hermes и бота после
перезагрузки Linux VM с последующим ответом через Ollama в Telegram.
Также выполнена одноразовая cron-задача постоянного шлюза с локальным
результатом при закрытом Telegram-клиенте, по подтверждению пользователя.
Отказ постороннему ещё требует фактической проверки.

Работа выполняется вдвоём с одним общим отчётом. Владельцем Telegram-шлюза
остаётся один пользователь; второй участник может проверить отказ
постороннему аккаунту, не добавляя свой ID в allowlist.

Время новых проверок приводится в зоне `America/Los_Angeles` с учётом
PDT/PST. Машинные материалы сохраняют исходные UTC-поля и дополнительно
содержат местное время. Даты ранних записей подготовки сохранены по их
первичным материалам.

16 октября добавлен выбор Ollama на Mac и в Docker. Для CPU-модели
память VM увеличена до 10 GiB; таблица первоначальной среды ниже сохраняет
состояние проверки от 15 октября. Новая конфигурация и отдельные технические
замеры опубликованы в [сравнении backend](ollama-backends.md).

## Доступ к Telegram

Токен создаётся владельцем через `@BotFather` и вводится только локально.
Для текущего стенда подготовлена команда `./scripts/lab.sh setup --gateway-only`:
она запускает собственный локальный мастер, сохраняя настройки Ollama.
Порядок ввода токена, ID и включения API приведён в
[инструкции управления](local-setup.md#настройка-hermes-и-telegram).
Контекст памяти согласован с P1: другие исследования и эксперименты
остаются за пределами текущего этапа.

В `TELEGRAM_ALLOWED_USERS` окружения собственного бота записывается один
числовой ID. `Owner` разрешает только его личные сообщения; группы и
посторонние сообщения отбрасываются до вызова Hermes. Allow-all выключен,
дополнительные списки доступа пусты. Native Telegram Hermes отключён;
запуск агента через локальный API требует отдельного случайного ключа.

Проверка перед запуском отклоняет пустой ID, отсутствующий токен,
allow-all и посторонние ID в общем списке. Успешная проверка конфигурации
не доказывает отказ реальному Telegram-аккаунту: для этого нужен отдельный тест.

### Собственный Telegram-код

По выбранному референсу `crudik` созданы `entities`, `application`,
`adapters`, `presentation` и `main`. Бот принимает Update через aiogram,
проверяет владельца в приложении и передаёт текст в Hermes через
`/v1/runs`. Сборка зависимостей — Dishka; история и инструменты остаются
в Hermes. [Описание кода и эксплуатации](telegram-bot.md).

Сохранённые токен и ID перенесены внутри VM без повторного ввода и
публикации. API включён на loopback `127.0.0.1:8642`; запрос запуска без
ключа получил HTTP 401. Подтверждены права `0600`, UID/GID 10000,
совпадение ключей двух сервисов и начало polling. Проверка состояния API
не заменяет пользовательский диалог и выполнение инструментов.
Обезличенные сведения — [custom-telegram-bot.json](../evidence/p1/custom-telegram-bot.json).

16 октября в 11:04:18 PDT (UTC−07:00) реальный `HermesGatewayImpl` получил
ожидаемое «готов» через API и локальную `agent-lab-qwen:4b`; первый запрос
занял 51,76 секунды. Runtime запроса подтвердил `provider=custom` и выбранную
модель; Ollama показала 100% GPU и контекст 65 536. Это одна техническая
проверка генерации, без передачи сообщения через Telegram и без замера
средней скорости или надёжности.

После сообщения владельца об отправленных `/start` и текстовом запросе
выполнена отдельная проверка журналов: новых событий обработчиков,
Telegram-запусков `/v1/runs` и сессии владельца не найдено. Токен действителен,
webhook отключён, очередь Telegram пуста. Получателя нужно сверить по
имени бота; успешный диалог пока не подтверждён.
При дополнительной диагностике Python-процесс внутри контейнера вызвал
OOM и один автоматический перезапуск; отсутствие событий было обнаружено
ещё до этого инцидента. Дальнейшие обращения к Telegram API выполнялись
из VM вне контейнера бота. Факты и границы вывода сохранены в
[telegram-dialogue-attempt.json](../evidence/p1/telegram-dialogue-attempt.json).

Последующая сверка подтвердила: присланное имя бота совпадает с `getMe`,
числовой ID — с разрешённым владельцем. В 11:30:40 PDT (UTC−07:00)
получатель кратко остановлен для прямого чтения очереди без `offset`;
очередь оказалась пустой, затем получатель снова запущен. Hermes и Ollama
продолжали работать. Причина отсутствия прежних сообщений не установлена;
для проверки нужны новые сообщения владельца после этой сверки.

Позже 16 октября бот успешно отправил два ответа: в 11:46:55 и 11:46:57
PDT (UTC−07:00). Присланный владельцем снимок подтверждает получение справки
и ответа на `/status`. Эти команды обходятся без модели; на 11:48:31 PDT
Telegram-запусков агента в Hermes всё ещё 0. Это подтверждение приёма и
отправки служебных сообщений, но ещё не генерации через Ollama.
Материалы — [telegram-commands.json](../evidence/p1/telegram-commands.json)
и [исходный снимок](../evidence/p1/telegram-commands.png).

В 13:00:10 PDT (UTC−07:00) 16 октября Hermes принял настоящий текстовый
запрос из Telegram: «Ответь одним словом: готов». В сохранённой беседе
подтверждены вопрос и ответ «Готов.». Запуск завершился со статусом
`completed`, runtime указал `provider=custom`, модель `agent-lab-qwen:4b`.
В 13:01:03 бот записал `reply_sent` после успешного вызова Telegram API.
От принятия запуска до отправки ответа прошло 52,180 секунды.

Следующий такой же вопрос также завершился и был отправлен в 13:01:04;
соответствующий интервал — 1,198 секунды. Запись использования модели
показывает 15 121 входной токен из кеша во втором запуске. В том же окне
журнал Ollama содержит три успешных `POST /v1/chat/completions` с HTTP 200;
дополнительный вызов не приписывается отдельному вопросу без сквозного ID.
Это две технические проверки диалога, без оценки средней скорости,
надёжности или автономности. Подтверждение чтения ответа владельцем
не запрашивалось: проверена успешная отправка через Telegram API.
Обезличенные материалы —
[telegram-ollama-dialogue.json](../evidence/p1/telegram-ollama-dialogue.json).

Проверки обработчиков используют настоящие aiogram/Dishka и локальный
HTTP-сервер Telegram API: справка, доступ владельца, отказ постороннему
и группе, отправка длинного Unicode-ответа. Контракт с Hermes проверен
через HTTPX, включая отмену, дедлайн и запрос остановки. Это автоматические
проверки на искусственных данных; реальный второй аккаунт ими не проверен.

Прямая доставка уведомлений планировщика в собственный бот пока не
реализована. Для автономного прогона P1 результат нужно фиксировать
в рабочем каталоге и истории Hermes; обещать уведомление в Telegram
на этом этапе нельзя.

### Проверка загрузки навыков — 17 октября

Первый этап завершения P1 выполнен в режиме Ollama на Mac. В 03:46:35
PDT (UTC−07:00) собственный бот записал `bot_polling_started`; API Hermes
отвечает на `/health` кодом 200. Журнал подготовки сообщает о 58 встроенных
файлах навыков. Это сообщение о синхронизации файлов само по себе не
доказывает, что агент прочитал их содержимое.

Отдельный контрольный запрос к Hermes API завершился в 03:50:48 PDT.
В сохранённом диалоге последовательно присутствуют реальные вызовы:

1. `skills_list` — 54 доступных навыка, среди них `lab-readiness`.
2. `skill_view` с `name=lab-readiness` — успешное чтение полного содержимого;
   SHA-256 совпал с `templates/skills/lab-readiness/SKILL.md` в репозитории.
3. `terminal` — выполнение команд навыка с кодом выхода 0: UID `10000`,
   `/opt/data/workspace`, Python `3.13.5`, `WORKSPACE_OK`.

Снимок индекса содержит 59 записей; каталог доступных навыков и индекс
имеют разное назначение. В этом прогоне полностью прочитан один навык,
остальные тела загружаются по требованию. Запрос явно называл навык;
неявное распознавание общего запроса этим наблюдением не проверялось.
Это техническая диагностика P1, без разработки исследовательского навыка P2.

Запуск занял 69,93 секунды, runtime подтвердил `provider=custom` и
`agent-lab-qwen:4b`. Указанные API 67 743 входных и 192 выходных токена
суммируются по шагам запуска; это не размер одного контекстного окна.
В финальном тексте модель неточно написала об отсутствии `.env` и токенов:
приватные файлы существуют, диагностика их не читала. Результат принят
по фактическим ответам инструментов, а не по этой формулировке модели.

При проверке обнаружена отдельная ошибка закреплённого Hermes:
`GET /v1/skills` возвращает HTTP 500, поскольку обработчик передаёт
неподдерживаемый `include_editorial` функции `_find_all_skills`.
Штатные `skills_list` и `skill_view` работают; код поставщика и версия
образа не изменялись. Собственный бот этот endpoint не использует.

Обезличенные данные — [skill-loading.json](../evidence/p1/skill-loading.json),
исходные временные метки Docker сохранены в
[журнале старта](../evidence/p1/skill-loading-startup.log).
Запрос выполнен через API постоянного шлюза; новый Telegram-диалог,
снимок экрана, перезагрузка, cron и отказ постороннему этим этапом
не подтверждаются.

## Проверки после подключения бота

### Диалог и журнал старта

1. Выполнить `./scripts/lab.sh gateway` и проверить оба контейнера.
2. Сохранить журнал старта: активный Telegram, отсутствие ошибок авторизации
   и подтверждение загрузки навыков. Перед включением в отчёт удалить
   токены, идентификаторы пользователей и личные сообщения.
3. Отправить `/start`, затем короткий текстовый контрольный запрос. Зафиксировать ответ,
   условия замера времени отклика и снимок диалога без личных данных.

### Восстановление после перезагрузки VM

1. При работающем шлюзе записать boot ID VM, ID контейнера и время его старта.
2. Перезагрузить гостевую ОС. Mac и его пользовательская сессия остаются включены.
3. Дождаться восстановления SSH, туннеля, контейнера и Telegram без ручного
   `start`, `gateway` или `compose up` после ребута.
4. Сопоставить новый boot ID, время старта контейнера и журнал шлюза;
   получить контрольный ответ бота.

Этот тест относится к перезагрузке Linux VM. Холодный запуск Mac после
выключения и работа при спящем Mac в проверку не входят: Ollama и туннель
зависят от пользовательской сессии macOS.

Проверка выполнена 17 октября 2026 года, время Лос-Анджелеса — PDT
(UTC−07:00). Команда `sudo systemctl reboot` отправлена в 04:03:29.
Boot ID изменился с `ecce175f-7adf-4cb6-a15b-17d79eea956b` на
`9ed03e88-7439-4f82-a977-5b91bf2e1803`. Docker остался включён в автозапуск
и восстановил те же контейнеры с новыми временами старта:
Hermes — 04:03:39, бот — 04:03:44. После ребута не выполнялись
`start`, `gateway`, `compose up`, `docker start` или ручной перезапуск
служб. Образ, конфигурация и код приложения не менялись.

В 04:03:43 первая попытка запуска бота записала `bot_startup_failed`.

### Проверка постороннего аккаунта

17 октября 2026 года выполнена подготовка. Пользователь сообщил, что
доступа ко второму аккаунту пока нет; реальное сообщение не отправлялось,
отказ в Telegram и снимок экрана этим этапом не подтверждаются.

В работающем контейнере настроен ровно один числовой владелец, совпадающий
с сохранённым приватным окружением. Native Telegram выключен, оба флага
allow-all у Hermes имеют значение `false`, API слушает loopback.
Семь файлов, отвечающих за доступ, конфигурацию, обработку сообщений,
запуск, журналы и вызов Hermes, совпали с рабочими исходниками по SHA-256.
Настройки, allowlist и сервисы не менялись.

Выбранные 13 тестов прошли. Они используют настоящие обработчики
aiogram/Dishka, локальный HTTP-сервер вместо Telegram API и `AgentMock`:
посторонний отправитель и группа не получают ответа и не вызывают агента,
разрешённый запрос владельца передаётся агенту, недопустимые списки
владельцев отклоняются конфигуратором. Это автоматические проверки на
искусственных данных, а не обращение второго аккаунта к работающему боту.
Материалы — [outsider-preflight.json](../evidence/p1/outsider-preflight.json).

Для завершения требования:

1. Зафиксировать новое окно наблюдения при работающем шлюзе; до попытки
   проверить отсутствие других запросов и активных cron-задач.
2. С настоящего второго аккаунта отправить `/start` и уникальный текстовый
   контрольный вопрос в `@TestGermesBot`, не добавляя аккаунт в allowlist.
3. Зафиксировать отсутствие ответа и pairing. Сохранить снимок экрана
   с именем бота, контрольным вопросом и временем; скрыть личные данные.
4. Сопоставить попытку с `update_rejected`. Проверить отсутствие
   `hermes_run_admitted`, новых Telegram-запусков Hermes и генерации Ollama
   в выделенном окне. Анонимная запись отказа без связанной попытки
   второго аккаунта сама по себе недостаточна.
5. Закрыть окно проверки отказа, затем повторить отдельный запрос
   владельца и подтвердить доставку ответа: ограничения не должны
   блокировать его доступ.

## Локальная модель и расходы

Платный API и облачный fallback не подключены; у локального Ollama нет
кабинета провайдера с денежным лимитом. Поэтому требуемый снимок такой
панели отсутствует. Конфигурация локальной модели приложена как описание
выбранного варианта; её не следует выдавать за подтверждение денежного лимита.

Для процесса Ollama задан `OLLAMA_NO_CLOUD=1`, одна одновременно загруженная
модель и один параллельный запрос. Значения работающего launchd-сервиса
сверены с конфигурацией в [ollama-limits.json](../evidence/p1/ollama-limits.json).
В Hermes ограничены число ходов (8),
а в Compose — память, CPU и число процессов. Эти ограничения регулируют
потребление ресурсов. Затраты на электричество и оборудование не измерены.

## Применение ИИ

Codex использован для разработки скриптов управления, анализа конфигурации,
подготовки тестов и оформления отчёта. Инфраструктурные сведения получены
из команд на Mac и в отдельной VM. Проверки диалога, отказа постороннему,
перезагрузки шлюза и его планировщика добавляются только после реального
выполнения и проверки сохранённых материалов.
