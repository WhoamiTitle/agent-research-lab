# Собственный Telegram-бот перед Hermes

Код расположен в `src/agent_bot`. По выбранному пользователем референсу
`crudik` выделены `entities`, `application`, `adapters`, `presentation`
и `main`. Сам референс — приложение FastAPI; Telegram-обработчики написаны
для этого проекта на aiogram. Hermes продолжает хранить диалоги, выполнять
инструменты и обращаться к локальной Ollama.

```text
Telegram → aiogram / HandleMessage → HermesGateway → Hermes API → Ollama
                     ↓                                  ↓
               проверка Owner                    память и инструменты
```

## Ответственность кода

| Каталог | Ответственность |
| --- | --- |
| `entities/owner.py` | Один владелец; разрешены только его личные сообщения |
| `application/handle_message.py` | Проверка доступа, справка, статус, запрос агенту и понятные ошибки |
| `application/common/agent.py` | Порт `AgentGateway` и прикладные ошибки без зависимости от HTTP или Telegram |
| `adapters/hermes/` | HTTP-контракт Hermes, запуск, ожидание результата и запрос остановки |
| `presentation/telegram/` | Router, преобразование Update в запрос приложения и отправка частей ответа |
| `main/config/` | Типизированные настройки из приватного окружения |
| `main/di/` | Dishka: сборка зависимостей и закрытие HTTP/Telegram-сессий |
| `main/telegram.py`, `lock.py`, `logs.py` | Polling, блокировка второго процесса и JSON-журналы |
| `infra/bot/` | Docker-образ и локальный мастер настройки внутри VM |

Правило доступа выполняется до проверки здоровья или генерации. Посторонний
аккаунт и группа не получают ответа и не вызывают модель. Открытой регистрации,
pairing и изменения allowlist через Telegram нет.

`/start` и `/help` возвращают справку. `/status` проверяет HTTP-доступность
Hermes, без загрузки модели. Обычный текст передаётся агенту. Файлы, голосовые
сообщения и неизвестные команды получают подсказку об использовании текста.
Ответ отправляется обычным текстом частями до 2000 Unicode-символов, чтобы
учесть ограничение Telegram и символы вне BMP.

## Контракт с Hermes

Использован API закреплённого Hermes v0.21.6:

- `GET /health` — доступность сервера.
- `POST /v1/runs` с телом `{"input": "…"}` — запуск агента.
- `GET /v1/runs/{run_id}` — ожидание завершения и получение `output`.
- `POST /v1/runs/{run_id}/stop` — запрос остановки при отмене, ошибке,
  превышении срока или запросе ручного подтверждения.

Для защищённых запросов HTTPX передаёт Bearer-ключ. В `Idempotency-Key`
попадает `telegram-{update_id}`: повтор того же Update использует серверную
идемпотентность Hermes. Заголовок `X-Hermes-Session-Key` закрепляет одну
беседу владельца за постоянным ключом без его Telegram ID. История находится
в Hermes; отдельная БД боту сейчас не требуется.

Polling обрабатывает сообщения последовательно через
`handle_as_tasks=False`. Hermes ограничен одним API-запуском одновременно.
HTTP-запрос ограничен 15 секундами, весь запуск — 300 секундами; интервал
опроса — 1 секунда, запрос остановки — до 5 секунд. Отмена распространяется
после попытки остановки, сессии закрываются владельцем в Dishka.

Подтверждения опасных действий через этот интерфейс пока не реализованы:
бот запрашивает остановку и сообщает владельцу о необходимости подтверждения.
Отправка запроса остановки сама по себе не доказывает завершение агентской
задачи. Если соединение оборвалось до получения `run_id`, результат запуска
может быть неизвестен клиенту.

Отдельной надёжной очереди исходящих ответов нет: повторная генерация
ограничивается идемпотентностью Hermes, но доставка в Telegram не гарантирует
«ровно один раз». При ошибке отправки сохраняется `telegram_delivery_failed`.
Планировщик продолжает работать в Hermes; автоматическая пересылка его
уведомлений в собственный Telegram-интерфейс пока не реализована.

## Настройка и запуск

Все команды выполняются из корня проекта на Mac:

По умолчанию используется Ollama на Mac. Для режима модели в Docker
сначала выбрать backend по [инструкции](ollama-backends.md); адрес
локального API для Hermes сохраняется. Выбор модели не запускает бота.

```sh
./scripts/lab.sh start
./scripts/lab.sh sync
./scripts/lab.sh setup --gateway-only
./scripts/lab.sh gateway
```

Мастер запрашивает токен и один ID через скрытый локальный ввод. Он сохраняет
файлы с правами `0600` и UID/GID 10000, создаёт резервную копию, устанавливает
официальный extra Hermes `messaging` для его управляемого окружения, отключает
native Telegram и включает API на loopback. Полный мастер `setup` сохраняется
для настройки модели; после него нужно выполнить `setup --gateway-only`.

| Файл внутри VM | Содержимое |
| --- | --- |
| `/srv/agent-lab/bot/.env` | `TELEGRAM_BOT_TOKEN`, один `TELEGRAM_ALLOWED_USERS`, `HERMES_API_KEY` |
| `/srv/agent-lab/data/.env` | Параметры локальной модели и совпадающий `API_SERVER_KEY`; токен Telegram пуст |
| `/srv/agent-lab/data/config.yaml` | `platforms.telegram.enabled=false`, API `127.0.0.1:8642`, один API-запуск |
| `/srv/agent-lab/backups/bot-setup-*` | Приватные резервные копии перед изменением; также содержат секреты |

Значения не нужно вводить повторно при обычном запуске. Для смены токена
или ID снова используется мастер. Ключ API создаётся внутри VM и повторно
используется при следующей настройке. Примеры файлов в `templates/` не
содержат действующих значений.

`gateway` проверяет конфигурацию и Ollama, собирает образ, поднимает Hermes
и ждёт HTTP-healthcheck, затем запускает `agent-research-telegram`.
Оба сервиса имеют `restart: unless-stopped`. У бота read-only rootfs,
UID 10000 и отдельный том для его настроек и `polling.lock`; Docker-сокет,
каталоги Hermes и файлы Mac ему не передаются. API доступен только в сети VM
на loopback. Служебные проверки и конфигуратор обходят init образа Hermes,
чтобы не запускать дополнительный шлюз.

Настройка возвращает исходные конфигурационные файлы при ошибке. Уже
установленные зависимости этим откатом не удаляются. При ошибке последующего
запуска `gateway` не возвращает старый Telegram-адаптер автоматически:
нужно устранить причину либо явно восстановить приватную копию и прежнюю
конфигурацию Compose. Одновременно запускать оба Telegram-адаптера нельзя.

## Журналы и проверки

Журналы собственного бота выводятся в JSON с зоной `America/Los_Angeles`
и явным смещением UTC. Собственные события имеют постоянные имена:
`bot_polling_started`, `hermes_run_admitted`, `hermes_run_completed`,
`reply_sent`, `update_rejected`. Токены, ID, текст диалога и сырые сообщения
зависимостей в эти записи не выводятся.

```sh
limactl shell agent-research -- sudo docker logs --tail 30 agent-research-telegram
./scripts/lab.sh status
```

`make check-ci` проверяет CLI и бота. В `tests/bot` есть реальные
aiogram/Dishka-обработчики с локальным HTTP-сервером Telegram API,
HTTPX-проверки контракта Hermes, отмена, сроки ожидания, блокировка второго
процесса и возврат настроек при сбое. Эти проверки не отправляют сообщения
реальному Telegram-аккаунту. Для приёмки владелец отдельно отправляет `/start`
и текстовый запрос; коллега проверяет отказ со своего аккаунта.

17 октября повторно прошли 13 выбранных тестов обработчиков и конфигурации.
Семь ключевых файлов работающего контейнера совпали с исходниками по SHA-256;
в его окружении настроен один владелец. Реальный отказ второму аккаунту
ещё не проверен: у пользователя пока нет такого аккаунта для прогона.
Результат подготовки и оставшиеся действия находятся в
[outsider-preflight.json](../evidence/p1/outsider-preflight.json) и
[протоколе P1](p1.md#проверка-постороннего-аккаунта).

Hermes и локальную Ollama. Получен ответ «Готов.», в журнале подтверждена
